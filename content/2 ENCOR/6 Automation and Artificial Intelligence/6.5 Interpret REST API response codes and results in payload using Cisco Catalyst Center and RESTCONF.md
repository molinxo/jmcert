A interpretação correta das respostas de uma API é essencial na automação de redes. Não basta verificar se a requisição foi aceita; é necessário confirmar se a operação foi realmente concluída e se o estado da rede foi alterado conforme esperado. A validação deve ocorrer em quatro etapas: verificar o sucesso da conexão (TLS/HTTP), analisar o código HTTP, interpretar o conteúdo da resposta (payload) e confirmar a alteração diretamente no dispositivo ou controlador.

## Fundamentos de REST API

As APIs REST utilizam métodos HTTP para realizar operações sobre recursos:

- **GET:** consulta informações (**safe** e idempotente).
- **POST:** cria recursos ou inicia ações (normalmente **não idempotente**).
- **PUT:** substitui um recurso (geralmente **idempotente**).
- **PATCH:** altera parcialmente um recurso (a idempotência depende da implementação).
- **DELETE:** remove um recurso (geralmente **idempotente**).

A lógica de repetição (retry) deve considerar tanto o método HTTP quanto o código de resposta. Repetir um **GET** normalmente é seguro, enquanto repetir um **POST** pode criar recursos duplicados.

Principais cabeçalhos HTTP:

- **Authorization:** credenciais ou token.
- **Accept:** formato esperado da resposta.
- **Content-Type:** formato dos dados enviados.
- **Location:** URI do recurso criado (201 Created).
- **Retry-After:** tempo recomendado antes de tentar novamente.
- **ETag / If-Match:** evitam sobrescrever alterações simultâneas.

Boas práticas de segurança:

- Utilizar sempre **HTTPS**.
- Validar certificados TLS.
- Nunca utilizar `verify=False` ou `curl -k` em produção.
- Não armazenar senhas ou tokens diretamente no código.
- Utilizar contas com privilégio mínimo e gerenciadores de segredos.

## Catalyst Center (Cisco DNA Center)

O **Cisco Catalyst Center (antigo DNA Center)** é um controlador que expõe APIs REST para automação da infraestrutura.

Características:

- Comunicação ocorre com o controlador, não diretamente com os dispositivos.
- Muitas operações são **assíncronas**.
- Autenticação normalmente gera um **token**, utilizado posteriormente no cabeçalho:

```
Authorization: Bearer <token>
```

Se o token expirar, a API retorna:

```
401 Unauthorized
```

Nesse caso, o script deve solicitar um novo token.

---

## Operações Assíncronas

Em muitas chamadas, o controlador responde imediatamente, mas continua executando a tarefa em segundo plano.

Os retornos mais comuns são:

- **202 Accepted** → requisição aceita, ainda em processamento.
- **200 OK** → pode conter informações da tarefa.

Normalmente o payload contém informações como:

- taskId
- status
- progress
- isError
- startTime
- endTime

Fluxo recomendado:

1. Autenticar.
2. Enviar a requisição.
3. Armazenar o **Task ID**.
4. Consultar periodicamente o status (polling).
5. Aguardar conclusão.
6. Verificar se a configuração realmente foi aplicada.

Mesmo quando:

```
"isError": false
```

a alteração ainda deve ser confirmada consultando o estado da rede.

Durante o polling recomenda-se utilizar **Exponential Backoff** e respeitar o cabeçalho **Retry-After**, evitando excesso de consultas (HTTP 429).

## RESTCONF

O **RESTCONF** permite acessar diretamente dispositivos utilizando modelos **YANG** através de HTTP/HTTPS.

Características:

- Comunicação direta com o equipamento.
- Geralmente utiliza autenticação HTTP Basic (IOS XE).
- Recursos são acessados por caminhos iniciados em:

```
/restconf/data
```

Exemplo:

```
/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
```

O RESTCONF diferencia:

- **Configuração (Config Data)** → intenção de configuração.
- **Estado Operacional (Operational Data)** → estado real da interface.

Uma interface pode estar configurada como habilitada (`enabled`), mas continuar operacionalmente inativa (`oper-status`).

Tipos de mídia mais utilizados:

```
application/yang-data+json
application/yang-data+xml
application/yang-patch+json
```

## Principais códigos HTTP

|Código|Significado|Ação esperada|
|---|---|---|
|**200 OK**|Operação concluída|Analisar o payload|
|**201 Created**|Recurso criado|Verificar o cabeçalho Location|
|**202 Accepted**|Requisição aceita, ainda executando|Consultar o status da tarefa|
|**204 No Content**|Operação concluída sem conteúdo|Não há payload para interpretar|
|**400 Bad Request**|Requisição inválida|Corrigir parâmetros|
|**401 Unauthorized**|Autenticação inválida|Obter novo token|
|**403 Forbidden**|Sem permissão|Verificar privilégios|
|**404 Not Found**|Recurso inexistente|Validar URI|
|**409 Conflict**|Conflito de estado|Corrigir inconsistências|
|**429 Too Many Requests**|Muitas requisições|Respeitar Retry-After|
|**500/503**|Erro do servidor|Repetir posteriormente, se apropriado|

---

## Interpretação do Payload

O código HTTP sozinho não garante sucesso da operação.

Exemplos:

- **200 OK** pode conter:

```
"isError": true
```

indicando falha da aplicação.

- Um **400** ou **409** normalmente informa, no corpo da resposta, o motivo detalhado do erro (valor inválido, recurso duplicado, caminho incorreto, etc.).
