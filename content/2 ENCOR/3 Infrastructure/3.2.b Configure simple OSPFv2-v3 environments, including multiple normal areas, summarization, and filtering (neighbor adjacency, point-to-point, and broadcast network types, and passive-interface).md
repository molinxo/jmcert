O **OSPFv2** é utilizado para **IPv4** e o **OSPFv3** para **IPv6** (também suporta IPv4 por **Address Families**). Ambos utilizam o algoritmo **Dijkstra (SPF)** e organizam a rede em **áreas** para melhorar a escalabilidade.

## Configuração básica OSPFv2 (IPv4)

```
router ospf 1
 router-id 1.1.1.1
 network 192.168.1.0 0.0.0.255 area 0
 network 10.1.1.0 0.0.0.255 area 0
```


```
interface GigabitEthernet0/0
 ip address 192.168.1.1 255.255.255.0
 ip ospf 1 area 0
```

## Configuração básica OSPFv3 (IPv6)

```
ipv6 unicast-routing

router ospfv3 1
 router-id 1.1.1.1

interface GigabitEthernet0/0
 ipv6 address 2001:db8:1::1/64
 ospfv3 1 ipv6 area 0
```

## Áreas OSPF

- **Area 0 (Backbone):** Área principal da rede.
- **Áreas Normais:** Dividem a rede para reduzir o processamento e o tamanho da LSDB.

## Neighbor Adjacency

Os roteadores formam vizinhanças por meio de pacotes **Hello**.

**Requisitos:**

- Mesmo Area ID.
- Mesmos Hello/Dead Timers.
- Mesmo tipo de rede.
- Autenticação compatível (se utilizada).
- Endereçamento compatível.

## Tipos de Rede

- **Point-to-Point:** Não elege DR/BDR.
- **Broadcast (Ethernet):** Elege **DR** e **BDR**.

## Route Summarization

Agrupa várias rotas em um único prefixo para reduzir a tabela de roteamento.

**OSPFv2**

```
router ospf 1
 area 1 range 10.10.0.0 255.255.252.0
```

**OSPFv3**

```
router ospfv3 1
 address-family ipv6 unicast
 area 1 range 2001:db8:0::/64
```

## Passive Interface

Anuncia a rede sem formar adjacências OSPF.

```
router ospf 1
 passive-interface GigabitEthernet0/0
```

ou

```
router ospfv3 1
 passive-interface GigabitEthernet0/0
```

## Route Filtering

Controla quais rotas são anunciadas ou aceitas entre áreas ou durante redistribuição, utilizando recursos como **filter-list**, **prefix-list** e **route-map**.

## Verificação

```
show ip ospf neighbor
show ip ospf interface brief
show ip route ospf

show ospfv3 neighbor
show ipv6 route ospf
show ospfv3 interface
```

1. Criar os containers
```
docker run -d --name R1 --hostname R1 --privileged --network none quay.io/frrouting/frr:10.3.1
docker run -d --name R2 --hostname R2 --privileged --network none quay.io/frrouting/frr:10.3.1
docker run -d --name R3 --hostname R3 --privileged --network none quay.io/frrouting/frr:10.3.1
docker run -d --name R4 --hostname R4 --privileged --network none quay.io/frrouting/frr:10.3.1

docker ps
```

2. Habilitar os daemons OSPF

Vêm desligados por padrão:

```
docker exec R1 sed -i 's/^ospfd=no/ospfd=yes/; s/^ospf6d=no/ospf6d=yes/' /etc/frr/daemons
docker exec R2 sed -i 's/^ospfd=no/ospfd=yes/; s/^ospf6d=no/ospf6d=yes/' /etc/frr/daemons
docker exec R3 sed -i 's/^ospfd=no/ospfd=yes/; s/^ospf6d=no/ospf6d=yes/' /etc/frr/daemons
docker exec R4 sed -i 's/^ospfd=no/ospfd=yes/; s/^ospf6d=no/ospf6d=yes/' /etc/frr/daemons

docker restart R1 R2 R3 R4
sleep 5
docker ps
```

3. Criar os links

Link R1–R2:

```
sudo ip link add r1-r2 type veth peer name r2-r1
sudo ip link set r1-r2 netns $(docker inspect -f '{{.State.Pid}}' R1)
sudo ip link set r2-r1 netns $(docker inspect -f '{{.State.Pid}}' R2)
docker exec R1 ip link set r1-r2 up
docker exec R2 ip link set r2-r1 up
```

Link R2–R3:

```
sudo ip link add r2-r3 type veth peer name r3-r2
sudo ip link set r2-r3 netns $(docker inspect -f '{{.State.Pid}}' R2)
sudo ip link set r3-r2 netns $(docker inspect -f '{{.State.Pid}}' R3)
docker exec R2 ip link set r2-r3 up
docker exec R3 ip link set r3-r2 up
```

Link R3–R4:

```
sudo ip link add r3-r4 type veth peer name r4-r3
sudo ip link set r3-r4 netns $(docker inspect -f '{{.State.Pid}}' R3)
sudo ip link set r4-r3 netns $(docker inspect -f '{{.State.Pid}}' R4)
docker exec R3 ip link set r3-r4 up
docker exec R4 ip link set r4-r3 up
```

4. Criar as redes de cliente (dummy)
```
for i in 0 1 2 3; do
  docker exec R1 ip link add lb$i type dummy
  docker exec R1 ip link set lb$i up
  docker exec R4 ip link add lb$i type dummy
  docker exec R4 ip link set lb$i up
done
```

5. Endereçamento

R1:

```
docker exec R1 vtysh -c "conf t" \

 -c "interface lb0"   -c " ip address 172.16.0.1/24" \
 -c "interface lb1"   -c " ip address 172.16.1.1/24" \
 -c "interface lb2"   -c " ip address 172.16.2.1/24" \
 -c "interface lb3"   -c " ip address 172.16.3.1/24" \
 -c "end" -c "write memory"
```

R2:

```
docker exec R2 vtysh -c "conf t" \
 -c "interface lo"    -c " ip address 2.2.2.2/32" \
 -c "interface r2-r1" -c " ip address 10.0.12.2/30" -c " ipv6 address 2001:db8:12::2/64" \
 -c "interface r2-r3" -c " ip address 10.0.23.2/24"  -c " ipv6 address 2001:db8:23::2/64" \
```

6. Validar antes de começar

```
docker exec R1 ping -c2 10.0.12.2
docker exec R2 ping -c2 10.0.23.3
docker exec R3 ping -c2 10.0.34.2
```

Os três precisam responder. A partir daqui, nenhum OSPF está configurado — o resto é com você.

Para entrar em um roteador: `docker exec -it R1 vtysh`

### Desafios
#### 1 — Adjacência básica

Faça R1↔R2 formarem adjacência na área 1 e R2↔R3 na área 0. Inclua os loopbacks e defina router-id manualmente.

Verifique: show ip ospf neighbor em R2 lista dois vizinhos em Full.

Dica: no FRR o network usa prefix-length, não wildcard. E a área precisa ser dotted — 0.0.0.1, não 1.

#### 2 — Network type point-to-point

Todos os links são ethernet, então o OSPF elege DR/BDR até onde não faz sentido. Configure R1–R2 e R3–R4 como point-to-point; deixe R2–R3 como broadcast.

Verifique: vizinho em p2p aparece como Full/-; em broadcast, como Full/DR ou Full/BDR. Compare Network Type no show ip ospf interface.

#### 3 — Eleição de DR

No segmento broadcast R2–R3, force R3 a ser sempre o DR.

Verifique: show ip ospf interface r3-r2.

Dica: existem dois critérios de desempate. Qual o OSPF avalia primeiro? E por que mudar só a priority pode não surtir efeito imediato?

#### 4 — Passive-interface

As redes lb0–lb3 são LANs de cliente: nada de hello por ali, mas as redes precisam ser anunciadas. Use abordagens diferentes:

R1: declare cada interface passiva individualmente
R4: torne tudo passivo por padrão e abra exceção para o link de trânsito

Verifique: show ip ospf interface lb0 indica passive, show ip ospf neighbor em R4 mantém o vizinho, e as redes aparecem em show ip route ospf do outro lado.

Pegadinha: passive-interface não remove a rede do OSPF. Confirme isso na tabela de rotas do vizinho.

#### 5 — Sumarização

Nos ABRs: R2 sumariza a área 1 em 172.16.0.0/22, R3 sumariza a área 2 em 192.168.0.0/22.

Verifique em R4: uma rota /22, não quatro /24.

Se não funcionar: interfaces tratadas como loopback são anunciadas como /32. Como forçar o anúncio da sub-rede inteira?

#### 6 — Filtering

A) Em R3, suprima apenas 192.168.2.0/24, mantendo o resto do sumário.
B) Em R2, use prefix-list para impedir que o sumário da área 1 saia para o backbone.

Verifique (B) em R4: a rota 172.16.0.0/22 some. Remova o filtro e confirme que volta.

Dica: A é variação do comando do desafio 5. B usa area X filter-list prefix NOME out — pense em qual área referenciar e o que out significa do ponto de vista do ABR.

#### 7 — OSPFv3

Repita o essencial em IPv6 nos links R1–R2 (área 1) e R2–R3 (área 0).

Verifique: show ipv6 ospf6 neighbor e show ipv6 ospf6 interface.

No OSPFv3 não existe network — a área é atribuída na interface. E o router-id continua em formato IPv4.

#### 8 — Troubleshooting

Salve o estado bom primeiro:

```
for R in R1 R2 R3 R4; do docker exec $R vtysh -c "show run" > /tmp/$R.good; done
```

Aplique uma falha por vez e diagnostique só com show:

#	Falha	Sintoma
1	hello-interval diferente em um lado do R3–R4	vizinho cai, sem log óbvio
2	R4 na área errada (0.0.0.9)	adjacência não sobe
3	link R1–R2 passivo em R1	vizinho some, rota do link permanece
4	R1 em p2p, R2 em broadcast	compare show ip ospf interface dos dois lados
5	docker exec R3 ip link set r3-r4 mtu 1400	trava em EXSTART/EXCHANGE

O caso 5 é o mais importante: EXSTART em prova é quase sempre MTU mismatch.
